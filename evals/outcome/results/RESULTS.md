# Outcome eval results: none vs current (superpowers + mattpocock-skills) vs foxdev

13 tasks x 3 arms x 3 runs = 117 graded runs. Sonnet (claude-sonnet-5-5) at low effort for the runs, Opus (claude-opus-5-5) at low effort for the blind judge (diff and task only, arm hidden). Total spend about 14 USD including judges. Full tables: `summary.md` (generated by `aggregate.py`), per-run grades and diffs under `runs/`.

Tasks: 10 core (3 features, 3 bug fixes, 2 refactors, 2 add-tests) plus 3 harder ones added after the first round looked saturated (a vague three-cause bug report, an expression-evaluator feature with many edge cases, an async memoizer with in-flight and eviction subtleties).

## Reading

- No skill fired in any of the 117 runs, and no subagent was spawned. In `current` the SessionStart hook injected its skill-use preamble and in `foxdev` the skill descriptions were loaded; the model still went straight to read, edit, run tests. So the three arms are behaviourally almost the same agent, and outcome differences are noise plus the prompt-size effect of loading the plugins.
- Correctness is at the ceiling for all arms. Every run passed the existing suite. The only hidden-test miss after correction was one foxdev run on py-hard-feat-expr (2 of 56 tests).
- Test quality, coverage and mutation score are indistinguishable (paired differences have confidence intervals straddling zero). The refactor tasks and ts-feat-range have the lowest mutation scores for every arm.
- Cost: `current` costs about 0.01-0.02 USD more per run than `none` (roughly +15%) and `foxdev` about 0.01 more (+8%); both paired differences exclude zero. This is the plugins' added context, with nothing gained in return on these tasks. Time per run is the same.
- Judge scores: `foxdev` is 0.2 lower on design than `none`/`current` and `current` is slightly lower on readability; with one judge call per run and 39 runs per arm these are within what single-judge noise can produce, and the paired CIs mostly include zero. Do not read them as real.

## Caveats

- Saturation: these are small repos with direct, issue-style prompts. Sonnet at low effort solves them in about 25 seconds without any process, so the eval can only show that the skills do no harm here and add cost. It cannot show whether skills help on larger, ambiguous or long-horizon work, or at higher effort where skills may fire.
- Three runs per cell, 13 tasks; tasks are the unit for the paired bootstrap, so confidence intervals are wide for anything but cost.
- The hidden tests of five tasks were corrected after round one because they over-specified behaviour the prompts left open (e.g. word-boundary truncation in slugify, whitespace inside `>= 1.2.3`, `.5h`, constructor-time vs set-time ttl validation). All three arms failed those cases identically, so no arm was favoured; all runs were regraded against the corrected tests.
- Mutation scores come from an in-house mutator scoped to changed lines (max 40 valid mutants, equivalent mutants not removed), so they are comparable across arms but not absolute. "Tests before implementation" is detected from tool order and is a heuristic (agents mostly write files through Bash).
- Judge: one Opus low-effort call per run, diff only. The diff can reveal arm traces (none appeared).
- A further batch of two more runs per cell was not started: the permission system denied launching it, so the 3-run plan is the complete data set.
